## Notes

- Window: `lists/use-task-list.ts` (store), `lists/page-window.ts` (pure rules), `lists/max-list-entries.ts` (the cap, own file), rows are absolutely positioned at `index * ROW_HEIGHT_PX`, rows of the window plus placeholders for the visible rows only. Jumps (no overlap with the window) wait 100 ms; moves next to the window load at once. The first answer starts the other pages of the first screen, because only it knows the length.
- `addLiveRowAbove` in the store is the hook for the live-update story (S16); page numbers do not count these rows.
- Rows got cheaper: a native checkbox instead of `v-checkbox-btn`, and `HoverTooltip.vue` creates a tooltip on mouse-over instead of one `v-tooltip` per cell. With the old rows the wheel check had 10 long frames and DOM/listeners did not return after leaving.
- Existing test changed: `TL-024 further pages load...` in task-lists.spec.ts expected all 65 rows after scrolling to the end and the pages in order 0..3. A window drops far pages by design, so it now expects the last row, no first row, and pages 0..3 once each (any order).
- Simulator: sorts the tasks once per list of tasks (WeakMap), else a page of 30,000 tasks was slower than a real backend.
- 1,000,000 entries: `e2e/support/many-entries.ts` raises the total through `page.route`, as the reference allows. 30,000 tasks of four modules: `manyTasks` in `e2e/support/tasks.ts`. Only /tasks is measured (the simulated tasks are mostly unassigned).
- Measurement: `npx playwright test list-measurement`; numbers in `e2e/measurements/*.json` (git-ignored) and in the output table. Typical: heap 7-9 MB, 2,500 DOM nodes, no long frame to 1 in ten seconds of wheel, heap at the bottom of each of four primary filters 7.3-7.6 MB (limit 150 MB).
- SRCH-018 deviation (see ASK-010): heap is compared with the first time the user left the list, DOM nodes and listeners with the state before the list opened.
- Open item: Firefox is not installed here, so `SRCH-025 ... in Firefox` is skipped with a message (`npx playwright install firefox` runs it). The cap (100,000 x 40 px = 4 million px) is below Firefox's limit of 17.9 million, proven by a unit test.
- A real scroll bar drag cannot be done in headless Chromium (no visible bars); drags are series of big `scrollTop` jumps 5 ms apart.
- Step 4 (COSTS.md) is left to the caller, as for earlier stories.
